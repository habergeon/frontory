# WGSL · 28 Compute와 경계

[시리즈 목차](../README.md) · [전체 기술 지도](../../../README.md)

단계: 수치 검증과 커널 설계 · 편집 가능한 예제 · 저장 ID: `wgsl-03`

## 목표와 학습 후 역량

- 커널별 경계 전략을 적용한다.
- 배치·동기화·수치 정확성을 함께 검증한다.

## 선수 지식

27단위 결과물과 기록을 이어 사용합니다. Compute와 경계 실험에 앞서 이전 입력과 기준 출력을 보관합니다.

## 핵심 개념과 설명

### 경계 통합

논리 원소 수와 invocation 수는 일치하지 않을 수 있습니다. 독립 kernel의 early return과 협력 kernel의 중립값 참여를 구분해 적용합니다.

### 검증 통합

정확성은 마지막 원소·부분 workgroup·반복 실행까지 확인해야 합니다. barrier와 메모리 배치가 맞아도 잘못된 수식은 별도 CPU 비교로 찾아야 합니다.

## 실습 준비

기존 wgsl-03 미리보기는 출발점입니다. 이후 과제 전체의 구현이나 검증을 대신하지 않습니다. 별도 localhost 또는 HTTPS 프로젝트에서 직접 구현하는 문서 안내 실습입니다. secure context, navigator.gpu, adapter 요청 결과를 확인하고 미지원 안내를 제공합니다. device.lost 처리와 자원 해제를 유지합니다.

연결된 예제는 출발점입니다. 아래 과제 전체가 완성된 코드는 아니며 예제의 지원 범위를 넘는 작업은 별도 프로젝트에서 수행하세요.

## 실습 과제

1. map·reduction·stencil을 길이 1·65·1003에 실행하고 CPU 기준과 비교하세요.
2. 독립 kernel의 접근 전 검사와 reduction의 모든 lane barrier 참여를 소스에서 표시하세요.
3. report.md에 마지막 원소·sentinel·최대 오차·전체 지연·장치 정보를 모아 완료 조건을 판정하세요.

## 관찰할 변수

| 변수 | 기준 조건 | 바꿀 조건 | 예상할 변화·검증 가설 |
| --- | --- | --- | --- |
| 원소 수 | 64의 배수 | 65와 1003 | 남는 lane을 올바르게 처리하면 누락 없이 CPU 결과와 일치할 것으로 예상합니다. |

표의 예상은 측정 결과가 아닙니다. 한 번에 한 조건만 바꾸고 실제 결과가 다르면 원인을 기록하세요.

## 완료 조건

- [ ] 세 커널·세 길이의 결과와 끝 원소 검사가 기록된다.
- [ ] 동기화 경로에 비균일 barrier나 그룹 간 대기 루프가 없다.

## 자가 점검

1. 경계 return을 reduction에 그대로 옮기면 왜 실패하나요?
2. 일치하는 결과 외에 재현을 위해 무엇을 남겨야 하나요?
