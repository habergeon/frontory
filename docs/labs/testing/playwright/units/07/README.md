# Playwright · 07 첫 흐름의 실패 진단

[시리즈 목차](../../README.md) · [전체 기술 지도](../../../../README.md)

단계: 사용자 흐름과 Locator · 문서 기반 직접 구현 · 저장 ID: `playwright-step-07`

## 목표와 학습 후 역량

- 학습 결과: 실패 위치의 역할을 설명한다. 입력 사례: 정상 제목과 의도적 잘못된 기대.
- 산출물: 실패 단계가 보이는 리포트. 단계 처리 근거를 코드와 연결해 설명한다.

## 선수 지식

6단위 「재시도 Assertion」의 상태 대기 및 실패 설명 실습 결과를 준비한다.

## 핵심 개념과 설명

### 실패 위치

탐색·선택·문서 열기를 분리해 확인한다. 마지막 화면만 비교하면 원인이 숨는다.

### 단계

test.step은 흐름의 의미를 리포트에 남긴다. 구현 세부마다 과도하게 쪼갤 필요는 없다.

## 실습 준비

모든 테스트는 별도 Node 프로젝트의 @playwright/test와 테스트 전용 로컬 origin에서 작성·실행한다. 기존 playwright-01·02·03 미리보기는 테스트 소스를 보여줄 뿐 iframe에서 Playwright를 실행하지 않는다. 새 테스트 파일은 과제에서 직접 작성하며 통과 여부는 실제 runner 출력으로만 판단한다. 사용자 profile·실사용 저장소를 사용하지 않고 CSP·격리를 유지한다.

이 단위에는 내장 실행 예제가 없습니다. 아래 절차에 따라 별도 실습 파일을 만들고 실행 결과를 필기에 남기세요. 코드 파일은 작업 폴더에서 따로 보관하고 Frontory 필기는 JSON 또는 Markdown으로 백업하세요.

## 실습 과제

1. 별도 실습 프로젝트의 tests/day-7.spec.ts에 탐색 테스트에 test.step과 의미 있는 assertion을 추가한다. 기존 1·14·28단위 예제는 출발점으로만 참고한다.
2. 입력 조건: 정상 제목과 의도적 잘못된 기대. 기준: 정상. 기준 조건에서 실행한 뒤 관찰값과 오류를 notes/day-7.md에 남긴다.
3. 변경 변수: 기대 제목. 변경값: 틀린 제목. 같은 입력 경로로 다시 실행한다. 저장할 산출물: 실패 단계가 보이는 리포트. 확인할 가설: 어떤 사용자 조건이 깨졌는지 드러난다. 실제 결과와 비교해 일치 여부 및 차이의 원인을 기록한다.

## 관찰할 변수

| 변수 | 기준 조건 | 바꿀 조건 | 예상할 변화·검증 가설 |
| --- | --- | --- | --- |
| 기대 제목 | 정상 | 틀린 제목 | 어떤 사용자 조건이 깨졌는지 드러난다. |

표의 예상은 측정 결과가 아닙니다. 한 번에 한 조건만 바꾸고 실제 결과가 다르면 원인을 기록하세요.

## 완료 조건

- [ ] 필수 산출물: 실패 단계가 보이는 리포트. 기준 및 변경 조건 각각의 결과가 있어 총 2조건을 비교할 수 있고, 입력값과 실행 환경을 함께 기록했다.
- [ ] 두 조건의 차이에 관한 설명에 다음 개념을 모두 연결했다: 실패 위치, 단계. 예상과 다른 항목은 원인 또는 미해결 이유를 1개 이상 적었다.

## 자가 점검

1. 이번 실습에서 실패 위치 개념은 어느 처리 단계에 영향을 주는가? 입력 사례: 정상 제목과 의도적 잘못된 기대.
2. 변경 변수: 기대 제목. 확인할 가설: 어떤 사용자 조건이 깨졌는지 드러난다. 실제 결과가 가설과 일치했는가? 단계 관점에서 근거를 설명하라.
